- 跑马灯跑5s停：

>  按下key1按键 ： 启动流水灯，同时（启动倒计时）5s后自动停止（要清除计数）；
>
>  按下key2按键：关闭，**并不再倒计时；**
>
>  再按key1重新 5s。

几种方法：

### **第一步：拆分角色（先定义状态，不要先写 if）**

1. 哪些是**状态标志**（用来描述现在系统处于什么模式）？
2. 哪些是**资源 / 条件**（按键输入、传感器输入）？
3. 哪些是**节拍源**（谁负责计时：SysTick / TIM / HAL_GetTick）？

拿你这个例子：

-  状态：`FlowingLight_run_flag`（流水灯是否允许运行）、`timer_en`（倒计时是否开启）
-  输入：KEY1（启动）、KEY2（停止）
-  节拍源：SysTick 1ms 中断，负责计数

### 第二步：定义每一个状态的转移规则（画文字状态机）

状态机，是根治反复改 bug 最好的工具，不用很复杂：

-  空闲态：
   -  触发：KEY1 按下 → 切换到运行态；count 清零，timer_en=1
-  运行态：
   -  触发 A：KEY2 按下 → 切回空闲态，关闭所有标志
   -  触发 B：count>=5000（5s 到）→ 切回空闲态

**所有的变化，都必须明确 “什么条件，从哪个状态跳到哪个状态，附带哪些变量重置”。**

### 第三步：划分责任边界（前台 / 后台分离，非常关键）

✅ 后台（中断 SysTick）权限： 只做：

-  满足 `timer_en==1` 时 count++
-  时间到：把 `FlowingLight_run_flag=0`，`timer_en=0`，count 清零 禁止：点亮 LED、读取按键、HAL_Delay、复杂判断

✅ 前台 while (1) 权限： 只做：

-  扫描按键，修改状态标志、开启 / 关闭 timer_en
-  根据 `FlowingLight_run_flag` 执行流水灯（最好是非阻塞版本）
-  扫描光敏传感器 禁止：在 while 里面靠长延时阻塞整个循环

>  口诀：**中断管时间、打标记；主循环干活、读输入**



### 为什么改了好多版才成功？

顺序代码（比如：开灯→延时→关灯）是**线性思维**，人脑天然擅长； 前台 + 中断协同代码是**并行思维**：两条执行流在同时跑，一个动作的结果，会被另一条流随时改写。 人脑不习惯并行推演，很容易漏掉时序组合。比如：

按下 KEY1，3 秒后手动关闭，count 停在 3000； 4.5s 再次按下 KEY1，count 从 3000 继续往上加，只剩 1.5s 就超时。

这不是能力问题，是思维范式切换：

-  以前：写代码 = 描述一串动作
-  现在嵌入式：写代码 = 描述一套状态、一套规则，硬件在不断采样、跳转

## 给你一个可长期坚持的练习方式，进步会快很多

1. 以后动手写之前，先在注释里写下你的状态转移，再写代码，不要边写边想；
2. 优先使用 `HAL_GetTick()` 非阻塞主循环方案，尽量少在中断里写业务逻辑（SysTick 只用来提供时基，业务逻辑放前台，调试难度直接下降一大截）；
3. 每写完一版，主动给自己设计测试用例：
   -  正常：按 KEY1，看是不是刚好 5s 停
   -  中途干预：启动 3s，按 KEY2 停止，再按 KEY1，看是不是重新 5s
   -  边界：快到 5s 的时候按 KEY1，观察行为
4. 每次改完 bug，简单记一句：刚才是什么原因？（这次就是：计数没有开关标志，count 持续累加）。同类坑踩一次，后面就不会再反复卡。
